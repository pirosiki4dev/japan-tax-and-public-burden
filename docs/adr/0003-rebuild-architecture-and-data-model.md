## 文脈

ADR 0002で全体の対象範囲と最初のリリースの範囲を決めた。全体の範囲は全自治体・全保険者の個別の値、過去の制度、税収・国民負担率との対応まで及ぶ。一方、最初のリリースは国税・地方税・社会保険料の法令上の制度と率・金額（レベル3まで）、e-Gov法令APIの監視に限られる。

旧版（`legacy-v0`）では、制度別・Issue番号別の分岐がコードに直書きされ、CLIに中核ロジックが混在し、監視設定と正本データの間で同じ情報を重複して保持していた。本ADRは、最初のリリースを小さく作りながら、全体の範囲へ作り直しなしで拡張できる構成を定める。

## 決定

### 1. データ形式

| 用途 | 形式 | 理由 |
| --- | --- | --- |
| 正本（人が編集・レビューする） | YAML 1.2 | Pull Requestの差分が読みやすく、原文とコメントを併記できる |
| 正本の検証 | JSON Schema（Draft 2020-12） | 言語に依存せず、利用者もデータ構造を確認できる |
| 配布物 | CSV、JSON | 表計算ソフトとプログラムの両方で使える |

- 負担項目は `config/sources.yaml` と同様に `data/burdens.yaml` の1ファイルに集約し、`burden_id` の昇順に並べる。根拠法令も `data/legal-sources.yaml` の1ファイルに集約し、`law_id` の昇順に並べる。一覧の見通しを優先する。
- 自治体別・保険者別の値のように件数が数千に及ぶものは、団体ごとのファイルに分ける（下記「全体の範囲へ拡張するとき」）。
- 配布物は正本から決定的に生成し、`dist/` にコミットする。CIで再生成した結果と差分がないことを検査する。

### 2. 実装言語・実行環境

- Node.js 24 LTS以上、TypeScript、ES Modulesとする。
- Node.jsの型除去機能で `.ts` を直接実行し、ビルド工程を持たない。型検査は `tsc --noEmit` でCIに組み込む。
- データ構造の正本はJSON Schemaとし、TypeScriptの型はSchemaから生成する。手書きの型とSchemaを二重に管理しない。
- 依存パッケージは、YAML解析、JSON Schema検証、型生成、型検査に必要なものに限る。

旧 `AGENTS.md` の「当面Node.jsのJavaScriptで実装し、TypeScriptへの移行は別途レビューする」は、本ADRをそのレビューとして置き換える。

### 3. フォルダ構成

```text
.
├── data/                       # 正本（手で編集する）
│   ├── burdens.yaml            # 負担項目（レベル1・2）と、期間ごとの率・金額、日付、監視する条項（レベル3）
│   ├── groups.yaml             # 集計用グループ
│   ├── legal-sources.yaml      # 根拠法令（e-Gov法令ID、確認済みの改正版）。監視対象の一覧を兼ねる
│   ├── published-sources.yaml  # 告示等の値を公表する公式ページの確認済みの状態（掲載資料のリンクとSHA-256）
│   └── scope-decisions.yaml    # 個別判断で対象とした負担の記録
├── config/
│   └── sources.yaml            # 巡回する公式サイトのURL（唯一の置き場所）
├── schemas/                    # JSON Schema（データ構造の正本）
├── src/
│   ├── domain/                 # 純粋な規則（日付、状態の導出、整合性）。I/Oを持たない
│   ├── data/                   # 正本の読み込みと検証
│   ├── build/                  # 配布物の生成
│   ├── monitor/                # 巡回先の監視（共通の処理と、巡回先ごとのディレクトリ。例: egov/）、Issueの作成
│   └── cli/                    # コマンドの入口（引数の解析と表示だけ）
├── tests/
│   └── fixtures/               # 外部通信なしで使う公式応答の保存版
├── dist/                       # 配布物（生成物。手で編集しない）
├── docs/
│   └── adr/                    # 設計判断の記録
├── surveys/
│   └── <survey-id>/            # 法令調査の作業場所（通常運用では使わない）
└── .github/workflows/
```

依存の向きは `cli → monitor・build・data → domain` とし（`monitor`・`build` は `data` にも依存できる）、`domain` は他の層とNode.jsの入出力APIに依存しない。この規則はCIで検査する。

`surveys/<survey-id>/` は、正本に登録する対象を決めるための法令調査の作業場所で、通常運用（検証、配布物の生成、監視）では使わない。通常運用の成果物と混ざらないよう、調査ごとにフォルダを分け、抽出条件、抽出結果、判定結果、調査報告に加えて、調査用のプログラム・Schema・テストもその中に置く。調査用のプログラムは `src/` を参照してよいが、`src/` から `surveys/` を参照してはならない（`src/` の依存方向の検査で、層の外への参照として検出する）。調査の記録は正本ではなく、正本（`data/`）に登録した根拠の記録である。

全体の範囲へ拡張するときは、次のように追加し、既存のファイルの構造は変えない。

| 拡張 | 追加先 |
| --- | --- |
| 自治体の条例上の税率、保険者ごとの料率 | 団体ごとのファイル（例: `data/jurisdiction-rates/<団体コード>.yaml`）。団体の一覧は `data/jurisdictions.yaml` |
| 減免、特例、経過措置（レベル4） | `data/reliefs.yaml`（`burden_id` で負担項目を参照） |
| 税収・徴収実績、国民負担率との対応（レベル5） | `data/revenues/`、`data/burden-ratio/` |
| 自治体・保険者等の公式サイトの監視 | `config/sources.yaml` と `src/monitor/` の取得方式の追加 |

### 4. データモデル

#### 負担項目とIDの単位

- 財務省の税目一覧等の既存の区分は採用せず、IDはこのシステムで採番する。
- 法律、政令、省令、施行規則等をたどり、e-Gov法令APIで取得できる**1つの率または金額**を1つの負担項目とし、1つの `burden_id` を付ける。
  - 累進税率は区分ごとに、標準税率と制限税率はそれぞれ、別の負担項目とする。
  - 負担者が異なれば別の負担項目とする（例: 労使折半の社会保険料は被保険者分と事業主分の2項目）。
- 納税義務者・負担者、課税対象、課税標準（レベル2）は負担項目ごとに持つ。

#### 識別子

| ID | 形式 | 例 |
| --- | --- | --- |
| `burden_id` | 区分の接頭辞と6桁の連番。`nt`: 国税、`lt`: 地方税、`si`: 社会保険料、`ot`: その他の公的負担 | `nt-000001` |
| `version_id` | 英小文字のkebab-case。`<burden-id>-v<連番>` を推奨 | `nt-000001-v1` |
| `group_id` | 英小文字のkebab-case | `income-tax` |
| `law_id` | e-Gov法令ID | `363AC0000000108` |

- `burden_id` には条文番号や名称等の意味を持たせない。条番号のずれや名称の変更でIDを変えないためである。
- 一度使った `burden_id` は、廃止後も削除・再利用しない。接頭辞は `category` と一致させ、CIで検査する。
- 団体を追加するときは、自治体は全国地方公共団体コード、保険者は保険者番号を使う。

#### 区分（`category` と `burden_id` の接頭辞）の判断基準

区分は、法令上だれが課す負担か（法的な性格）で判断する。徴収事務を行う主体や、実質が保険かどうかでは判断しない。接頭辞は `category` の英語名の頭文字で、このシステム独自のものである。

| 接頭辞 | `category` | 判断基準 | 根拠 |
| --- | --- | --- | --- |
| `nt` | `national_tax` | 国が課する税 | 国税通則法第2条第1号の「国が課する税」。同号が国税の定義から除く関税、とん税、特別とん税、森林環境税、特別法人事業税も、国が課する税なので `nt` とする |
| `lt` | `local_tax` | 道府県税または市町村税（法定税・法定外税） | 地方税法第1条第1項第4号 |
| `si` | `social_insurance` | 社会保険の各法律に基づく保険料・掛金 | 健康保険法、厚生年金保険法、国民年金法、介護保険法、労働保険の保険料の徴収等に関する法律等 |
| `ot` | `other_public_burden` | 上記に当たらない、ADR 0002の対象範囲の負担（法令に基づく賦課金・拠出金・負担金、個別判断で対象としたもの） | 各根拠法令、`data/scope-decisions.yaml` |

判断に迷いやすい例は次のとおり。

| 例 | 区分 | 理由 |
| --- | --- | --- |
| 森林環境税、特別法人事業税 | `nt` | 市町村・都道府県が徴収するが、国が課する税 |
| 地方法人税 | `nt` | 名称に「地方」を含むが、国が課する税 |
| 地方消費税 | `lt` | 道府県税 |
| 国民健康保険税 | `lt` | 実質は保険だが、地方税法第5条に定める市町村税 |
| 国民健康保険料 | `si` | 税ではなく保険料として課される |
| ユニバーサルサービス料 | `ot` | 電気通信事業法に基づく負担金。個別判断で対象としたかどうかでは接頭辞を分けない |

区分を追加する予定はない。ADR 0002の対象範囲は、上記の4区分のいずれかに当たる。

#### 法改正があったときのIDと版の扱い

| 改正の内容 | 扱い |
| --- | --- |
| 率・金額の変更、累進の区分の境界の変更 | 同じIDに版を追加する |
| 条番号のずれ、別の条・別の法令への移動 | 同じIDに版を追加し、新しい版の `provisions` に移動後の条項を記録する |
| 率・金額の新設（累進の区分の追加を含む） | 新しいIDを採番する |
| 廃止 | 最後の版に `application_end` を記録する。IDは削除しない |
| 1つの率の分割、複数の率の統合 | 元のIDの版を終了し、新しいIDを採番して `predecessors` に元のIDを記録する |
| 課す主体、負担者、対象の変更 | 新しいIDを採番する |

#### 負担項目（`burdens.yaml` の `burdens` の要素）

| 項目 | 内容 |
| --- | --- |
| `burden_id`、`name` | ID、名称（例: 所得税（課税所得195万円以下の部分）） |
| `category` | `national_tax`、`local_tax`、`social_insurance`、`other_public_burden` |
| `levying_body_type` | `national`、`prefecture`、`municipality`、`insurer` |
| `groups` | 所属する集計用グループ。複数可 |
| `predecessors` | 分割・統合で終了した前身の `burden_id` |
| `legal_bases` | 負担そのものの根拠の `law_id` と条項。複数可 |
| `liable_parties`、`taxable_objects`、`tax_base` | 納税義務者・負担者、課税対象、課税標準（レベル2）。原文と要約を併記 |
| `versions` | 版（下記） |
| `status` | `active`、`promulgated_not_effective`、`abolished` |
| `source_urls`、`checked_at` | 根拠URL（複数可）と確認日時 |

#### 版（負担項目の `versions` の要素）

率・金額、または根拠の条項の位置が変わるごとに版を追加し、段階的な適用は複数の版で表す。1つの版は1つの値を持つ。

| 項目 | 内容 |
| --- | --- |
| `version_id` | 版のID |
| `dates` | 公布日、施行日、適用開始日、徴収開始日を個別に持つ。それぞれ原文（和暦）、正規化値、または `unknown` と根拠不足の理由 |
| `rate` | 率・金額（下表） |
| `determination` | 値の決まり方。`stated`（条文に値が書かれている）、`calculated`（条文の算式から計算する）、`published`（告示等、e-Gov法令APIで取得できない公表物で定まる） |
| `formula` | `calculated`・`published` の場合の算式の原文と、値を求めた過程 |
| `provisions` | 監視する条項（`law_id`、e-Gov法令APIの `elm`、条項の原文表記、役割）。複数可 |
| `source_urls`、`checked_at` | 根拠URL（複数可）と確認日時 |

`rate` は次を持つ。

| 項目 | 内容 |
| --- | --- |
| `kind` | `proportional`（比例。累進の1区分を含む）、`fixed_amount`（定額）、`per_unit`（従量） |
| `role` | `statutory`（法定）、`standard`（標準税率）、`limit`（制限税率）、`reduced`（軽減） |
| `value`、`unit`、`per` | 値、単位、従量の基準数量 |
| `bracket` | 累進の区分のうち、この項目が適用される範囲 |
| `applies_to` | 対象の条件（原文と要約） |
| `raw_text` | 値を定める原文 |

`provisions` の役割と、値の決まり方ごとに必要な条項は次のとおりとし、CIで検査する。

| 役割（`role`） | 意味 |
| --- | --- |
| `value` | 値を定める |
| `formula` | 算式を定める |
| `delegation` | 政令・省令・告示等へ委任する |
| `condition` | 適用の条件を定める |

| 値の決まり方 | 必要な条項 |
| --- | --- |
| `stated` | `value` の条項 |
| `calculated` | `formula` の条項 |
| `published` | `formula` または `delegation` の条項 |

法律が政令・省令に委任している場合は、委任元の法律の条項と委任先の政令・省令の条項を、同じ負担項目の `provisions` に含めて監視する。告示で決まる値や算式で決まる値は、e-Gov法令APIで取得できる算式・委任の条項を監視する。

制度の状態（現行、施行前、廃止）は、版の日付と基準日から導出し、手入力の値と矛盾しないことを検査する。

#### 集計用グループ（`groups.yaml`）

複数の負担項目を括って集計するため、グループを定義し、負担項目の `groups` で所属を示す。グループは `parent_group_id` で入れ子にできる。

| 集計方法（`aggregation`） | 意味 | 例 |
| --- | --- | --- |
| `sum` | 所属する率・金額を足すと全体の負担になる | 消費税と地方消費税、労使折半の保険料の被保険者分と事業主分 |
| `progressive` | 区分ごとに計算して合計する（所属する項目は `bracket` を持つ） | 所得税の税率の各区分 |
| `select_one` | 条件によりどれか1つが適用される | 標準税率と軽減税率 |
| `classification` | 分類だけで、率・金額を合算しない | 国税全体 |

#### 根拠法令（`legal-sources.yaml` の `legal_sources` の要素）

| 項目 | 内容 |
| --- | --- |
| `law_id`、`title` | e-Gov法令ID、題名 |
| `reviewed_revision_id` | 人がマスタへの反映を確認した最新の改正版のID |
| `reviewed_at` | その確認日時 |

#### 公表ページの確認済みの状態（`published-sources.yaml` の `published_sources` の要素）

告示等、e-Gov法令APIで取得できない公表物で定まる値（`determination: published`）について、値を公表する公式ページの掲載資料を人が確認した状態を記録する。

| 項目 | 内容 |
| --- | --- |
| `source_id` | `config/sources.yaml` の巡回先のID |
| `documents` | ページの本文に掲載された資料（掲載順）。リンクの文字列（`title`）、URL（`url`）、ファイルのSHA-256（`sha256`） |
| `reviewed_at` | 人が掲載資料を確認した日時 |

### 5. 最初のリリースの監視方式

#### ファイルの役割

| ファイル | 役割 | 単位 | 主な内容 | 更新するとき |
| --- | --- | --- | --- | --- |
| `config/sources.yaml` | どこから取得するか（巡回先の設定） | 情報源（サイト・API） | 情報源のID、名称、基本URL、アクセス間隔の上限、有効・無効 | 巡回先を追加するとき（例: 自治体・保険者の公式サイト） |
| `data/legal-sources.yaml` | どの法令を監視し、どこまで人が確認したか | 法令 | e-Gov法令ID、題名、法令番号、確認済みの改正版ID（`reviewed_revision_id`）、確認日時 | 根拠法令を追加するとき、改正検知Issueを人が確認したとき |
| `data/published-sources.yaml` | 公表ページの掲載資料を、どこまで人が確認したか | 公表ページ | 巡回先のID、掲載資料のリンクの文字列・URL・SHA-256、確認日時 | 公表資料の変化のIssueを人が確認したとき |
| `data/burdens.yaml` | 何を記録するか（負担の正本） | 1つの率または金額 | ID、区分、負担者、グループ、版（率・金額、日付、値の決まり方、監視する条項） | 率・金額等が変わったとき、負担項目を追加するとき |

- 根拠法令を負担項目に含めないのは、1つの法令が多くの負担項目の根拠になり、確認済みの改正版は法令ごとに1つの値だからである。
- 巡回先を根拠法令に含めないのは、巡回先はサイト・APIの単位で、1つの巡回先（e-Gov法令API）からすべての法令を取得するからである。
- `config/` は収集の方法の設定、`data/` は公開する事実（正本）を置く。

#### 監視の流れ

```text
config/sources.yaml          data/legal-sources.yaml           data/burdens.yaml

                              （law_id、reviewed_revision_id）    （provisionsのlaw_idとelm）
```

1. 監視は `data/legal-sources.yaml` の法令を順に、`config/sources.yaml` のURLとアクセス間隔に従ってe-Gov法令APIに問い合わせる。
2. 現在施行中の改正版が `reviewed_revision_id` と異なれば、改正検知Issueを作成する。
3. `data/burdens.yaml` の `provisions` から、影響を受ける負担項目をIssueに列挙する。
4. 人が確認し、Pull Requestで `data/burdens.yaml`（値が変わる場合）と `reviewed_revision_id` を更新する。

#### 手順

1. 監視対象の法令は、`data/legal-sources.yaml` の一覧から決める。監視対象だけを別に列挙する設定ファイルは持たない。条項単位の監視対象は、各版の `provisions` から決める。
2. GitHub Actionsで定期的にe-Gov法令APIから各法令の現在施行中の改正版（`current_revision_status` が `CurrentEnforced` の版）を取得し、`reviewed_revision_id` と比べる。施行前の改正版（`UnEnforced`）は、施行されて現在施行中の版になったときに検知する。
3. 異なる場合は、法令ID、新旧の改正版、根拠URL、検知日時を記載したIssueを作成する。同じ法令の同じ改正版について未完了のIssueがある場合は、新たに作成しない。
4. 人がIssueを確認し、マスタへ反映するかを判断する。反映する場合も反映しない場合も、Pull Requestで `reviewed_revision_id` を更新し、そのIssueを閉じる。
5. 取得の失敗やAPIの応答形式の変化は、改正の検知と区別したIssueにする。同じ法令の同じ種類の失敗について未完了のIssueがある場合は、新たに作成しない。
6. 改正を検知した法令は、確認済みの版と現在施行中の版の全文を1回ずつ取得し、`provisions` の各条項の本文を照合して、結果（本文の変更、削除、附則・別表の番号のずれ等）を負担項目とともにIssueに記載する。出現順の番号で指す附則（`SupplProvision[n]`）は改正法令番号（`AmendLawNum` 属性）で、別表（`AppdxTable[n]`）は題名で同じ要素かを確かめ、番号がずれた場合は新しい番号を示す。

監視は1つのコマンド `npm run monitor` で、`config/sources.yaml` の有効な巡回先を順に実行する（`--dry-run` でIssueを作成せずに結果を表示する）。`src/monitor/` の直下には巡回先に共通の処理（リクエストの間隔の維持と再試行、失敗の分類、Issueの重複防止と作成、巡回先の順次実行）を置き、応答の解釈と判定のように巡回先ごとに異なる処理だけを巡回先ごとのディレクトリ（例: `src/monitor/egov/`）に置く。監視の処理がない巡回先は、実行しない旨を表示する。URLはプログラムに書かず、`config/sources.yaml` の `base_url` と `data/legal-sources.yaml` の `source_url` から作る。workflow は `.github/workflows/monitor.yml` で、定期実行の開始はユーザーが判断する。重複防止の目印は、Issue本文の先頭のHTMLコメント（`<!-- monitor: ... -->`）に置く。

告示等の値を公表する公式ページ（`data/published-sources.yaml` に確認済みの状態がある巡回先）は、次のとおり監視する。

1. ページを取得し、本文の領域に掲載された資料（PDF）のリンクの文字列とURLを取り出す。各資料を取得して、ファイルのSHA-256を求める。
2. 確認済みの状態と比べ、資料の追加・削除、リンクの文字列の変更、ファイルの変更（同じURLでの差し替えを含む）があれば、変化した資料と、ページまたは資料を根拠URLに持つ負担項目を記載したIssueを作成する。同じ掲載状態について未完了のIssueがある場合は、新たに作成しない。
3. 人がIssueを確認し、マスタへ反映するかを判断する。反映する場合も反映しない場合も、Pull Requestで `documents` と `reviewed_at` を更新し、そのIssueを閉じる。
4. 取得の失敗と、本文の領域や資料のリンクが見つからない場合（ページの構造の変化）は、変化の検知と区別したIssueにする。

監視の状態は正本の `reviewed_revision_id` と `data/published-sources.yaml` だけで管理するため、Actionsがリポジトリへ書き込む必要はなく、権限はIssueの作成に限る。

## 検討した代替案

| 案 | 採用しない理由 |
| --- | --- |
| JSONを正本にする | Pull Requestでの差分確認と、原文・コメントの併記がしにくい |
| 負担項目ごとにディレクトリを分ける | 1つの率・金額ごとに項目を分けるため項目数が多く、一覧の見通しが悪くなる |
| 自治体別・保険者別の値まで1ファイルにまとめる | 数千の団体に広がり、差分と競合の管理が難しくなる |
| JavaScriptのまま実装する | 全体の範囲ではデータ構造が大きく、型による検査の効果が大きい。ビルド工程なしで導入できる |
| Pythonで実装する | PDF解析等の利点はあるが、最初のリリースはe-Gov法令API（JSON）だけを扱うため決め手にならない |
| 監視対象を別の設定ファイルで管理する | 正本と同じ情報を二重に持つことになり、旧版の問題を繰り返す |

## 結果

- 負担項目を追加するときは、`data/burdens.yaml` の要素と、新しい根拠法令であれば `data/legal-sources.yaml` の要素、新しいグループであれば `data/groups.yaml` の要素を追加するだけで、コードと設定の変更を要しない。
- `determination: published` の値（告示等で公表される値）は、e-Gov法令APIの監視では値そのものの改定を検知できない。公表物は、値を公表する公式ページの掲載資料を監視する（#167）。資料の中の値は自動で読み取らず、人が確認する。
- 旧版のファイルはすべて削除し、上記の構成で作り直す。`AGENTS.md`、`README.md`、テンプレート、CIもこの構成に合わせて作り直す。
- 実装はサブIssueに分けて進める（例: 基盤とSchema、データ投入、配布物の生成、監視）。
